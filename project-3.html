why vulkan

OpenGL hides most of what the GPU is really doing. The driver tracks memory, synchronisation and pipeline state for you, which is convenient and also makes it hard to see where a frame's time goes. Vulkan removes that layer. Every allocation, every barrier and every piece of state is something you write yourself.

I wanted to understand those pieces first-hand, so I am building a renderer from scratch instead of following a finished engine. The aim is a small, readable codebase that I can explain line by line.

what works today

The renderer brings up the whole path from a window to pixels on screen. It loads Vulkan through volk, creates a Vulkan 1.4 instance with the extensions GLFW requires, and builds a window surface. It then enumerates GPUs and prefers a discrete one, falling back to an integrated GPU or the first device available.

  • Finds a graphics queue family, creates the logical device with the swapchain extension, and retrieves the queue.
  • Creates a swapchain that prefers an sRGB BGRA format, with FIFO presentation, and an image view for every swapchain image.
  • Allocates a command pool and command buffer, and creates two semaphores and a fence for synchronisation.
  • Each frame waits on the fence, acquires an image, records commands, submits them and presents.
  • Uses dynamic rendering instead of render passes. Image layout transitions are done by hand with pipeline barriers, from undefined to attachment-optimal for drawing, then to present-source for display.
  • Clears the swapchain image to a solid colour each frame. This confirms the whole path works before any geometry exists.

All of it lives in one class that also tears every object down in reverse order, so resources are released cleanly.

what is next

I am building it in small steps, each one running and testable before the next begins:

  • Validation layers and a debug messenger, so mistakes are reported straight away.
  • A graphics pipeline with GLSL shaders compiled to SPIR-V, and the first triangle.
  • Frames in flight, so the CPU can record the next frame while the GPU draws, and swapchain recreation on window resize.
  • Vertex and index buffers uploaded through a staging buffer.
  • Uniform buffers and descriptor sets, then a depth buffer and a rotating 3D model.
  • Texture loading, simple lighting, and GPU timing queries to measure each pass.

what i am learning

My main goal is the reasoning behind the API: why the work is split into pipelines, command buffers and queues, and what the synchronisation rules protect against. Writing the layout transitions and fence handling myself showed me what a driver normally does behind OpenGL calls. I come from OpenGL and GLSL, so this is the step that makes those calls concrete.
